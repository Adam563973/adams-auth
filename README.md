# Adams Auth

A GitHub Pages-ready account and beta-access portal. The frontend is static, but **real accounts, Google/Microsoft sign-in, persistent applications, admin approval and secure six-digit code redemption require the Supabase backend included here**. Until `config.js` and Supabase are configured, the site stays in setup mode and will not pretend that sign-ups or passwords have been saved.

## Included

- Email/password sign-up and sign-in
- Google sign-in and Microsoft sign-in (Supabase provider `azure`)
- Account overview, display-name profile, sign-out and password reset
- Apply for beta, status tracking (`pending`, `approved`, `declined`, `active`) and a six-digit redemption form
- Owner dashboard for `adamshahid153@gmail.com`: view applicants, approve and generate code, regenerate an expired/lost code, or decline/revoke an offer
- Codes are generated by a server-side Edge Function, hashed with a server-only pepper, bound to the applicant account, expire after 72 hours, are single-use, and lock after 8 incorrect attempts
- SQL schema, row-level security policies, trigger, and Edge Function
- Responsive styling and a11y-focused modal/keyboard behaviour

## Security choices

- The website **never shows or stores a readable password**. Supabase Auth handles credentials. Users can request a reset link instead.
- The Supabase `anon`/publishable key can be public in `config.js`; the **service-role key and `BETA_CODE_PEPPER` must never be committed to GitHub or placed in browser code**.
- Admin status is not granted by the frontend alone. The database policy and Edge Function both require the exact owner email and a confirmed identity.
- The invitation code is shown to the owner once after approval. The browser sends it to the email client only when the owner clicks **Draft email**; Adams Auth does not send emails automatically. The database stores only a peppered SHA-256 hash.
- Beta codes do not grant access just by being approved. The applicant must sign in with the same account and redeem the code.

## 1. Create Supabase project

1. Create a project at [Supabase](https://supabase.com/).
2. Open **Project Settings → API** and copy the project URL and the public anon/publishable key.
3. In **SQL Editor**, run `supabase/migrations/001_adams_auth.sql` in full.
4. Check that the `profiles`, `beta_requests`, and `beta_invites` tables exist and Row Level Security is enabled.

## 2. Configure the frontend

Edit `config.js`:

```js
window.ADAMS_AUTH_CONFIG = {
  SUPABASE_URL: "https://YOUR-PROJECT-REF.supabase.co",
  SUPABASE_ANON_KEY: "YOUR_SUPABASE_ANON_OR_PUBLISHABLE_KEY",
  OWNER_EMAIL: "adamshahid153@gmail.com"
};
```

Only the URL, public key, and owner email belong here. Never paste your service-role key into this file.

## 3. Configure sign-in providers

In **Supabase → Authentication → Providers**:

- Enable Email/password sign-in. Keep email confirmation enabled for safer account ownership verification.
- Enable Google, then add the OAuth client ID and client secret in the Supabase dashboard.
- Enable Azure (Microsoft), then add the OAuth client ID and secret. The frontend requests the `email` scope.

For Google/Microsoft provider setup, use the callback URL shown in Supabase’s provider configuration. For Azure, Supabase documents the callback as `https://<project-ref>.supabase.co/auth/v1/callback`.

Official guides:
- [Supabase Auth overview](https://supabase.com/docs/guides/auth)
- [Google sign-in](https://supabase.com/docs/guides/auth/social-login/auth-google)
- [Microsoft/Azure sign-in](https://supabase.com/docs/guides/auth/social-sign-in/auth-azure)

## 4. Set allowed URLs for GitHub Pages

After you enable GitHub Pages for the repository, go to **Supabase → Authentication → URL Configuration**.

- Set **Site URL** to your full GitHub Pages URL, for example `https://YOUR-USERNAME.github.io/adams-auth/`.
- Add that URL (and the matching redirect wildcard supported by Supabase, e.g. `https://YOUR-USERNAME.github.io/adams-auth/**`) to **Redirect URLs**.
- If testing locally, add your local development URL too (for example `http://localhost:8080/**`).

Replace the examples with the actual account/repository URL. OAuth redirect destinations must match the allowlist.

## 5. Deploy the beta workflow Edge Function

You need the [Supabase CLI](https://supabase.com/docs/guides/cli) for this step.

From this project folder:

```bash
supabase login
supabase link --project-ref YOUR-PROJECT-REF
supabase functions deploy beta-workflow
```

The function uses the standard Supabase runtime `SUPABASE_URL`, `SUPABASE_ANON_KEY` (or publishable-key equivalent), and `SUPABASE_SERVICE_ROLE_KEY` server-side. Verify these are available in your Supabase function environment.

Create a long random pepper of at least 24 characters and set it as a server-side secret (do not store it in this repository):

```bash
supabase secrets set BETA_CODE_PEPPER="PASTE-A-LONG-RANDOM-SECRET-HERE"
```

Use a password manager or a secure random generator for the pepper. If you rotate it, previously generated invitation codes will no longer validate.

Official guide: [Supabase Edge Functions and secrets](https://supabase.com/docs/guides/functions/secrets).

## 6. Enable GitHub Pages

1. Commit the contents of this folder to a GitHub repository (the `index.html` should be at the published root).
2. In repository **Settings → Pages**, publish from your chosen branch and root folder.
3. Update Supabase URL Configuration to your final URL.
4. Open the deployed site and test account creation, email confirmation, Google sign-in, Microsoft sign-in, application submission and password reset.
5. Sign up/sign in at `adamshahid153@gmail.com` and confirm the email/provider before testing the owner console.

The repository includes `.nojekyll` so GitHub Pages serves the files without Jekyll processing. You can preview the frontend through a local static server, e.g. `python -m http.server 8080`, then visit `http://localhost:8080/`.

## Owner workflow

1. An applicant signs in and selects **Apply for beta**.
2. Their request appears in **Beta requests** when the verified owner is signed in.
3. **Approve & generate code** creates a random six-digit invitation, valid for 72 hours. The plain code is only returned to the owner once. Use **Copy code** or **Draft email** to send it privately.
4. The applicant signs into the same Adams Auth account, opens **Beta programme**, enters the code and selects **Access beta**.
5. The server validates account binding, expiry, one-time use and attempt count, then activates the beta badge.
6. Declining sets the user-visible status to **Offer declined**. Regenerating an approved code invalidates the previous code.

## Important limitations

- This package contains application source code, not a live deployed service. A Supabase project, OAuth provider credentials, Edge Function deployment, GitHub Pages setup and email settings are not created automatically by downloading the ZIP.
- This version drafts an invitation email for the owner; it does not send mail from the server. The owner must review and send it.
- OAuth provider credentials belong in Supabase’s provider settings, not in this website repository.
- Review Supabase project access and test the SQL/RLS policies before inviting real users. The admin controls are designed around one verified owner email (`adamshahid153@gmail.com`).
